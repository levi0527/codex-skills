# Challenge an experiment design

Use before committing substantial resources, when repeated experiments do not discriminate explanations, or when the user asks to question a proposed direction. Critique the consequential assumptions, not every imaginable imperfection. The output should change a decision or clarify a limit.

For learning/conditioning mechanisms and demonstration data, use [the causal and data audit](causal-review.md). For racket-return capability use [the progression guide](racket-progression.md). Put the corrected design and subsequent conclusions in [the shared experiment record](../../research-cycle/references/experiment-record.md), keeping observation, causal attribution and hypothesis distinct.

## Reconstruct and try to refute the claim

State the actual task objective, the capability already demonstrated, the current failure, and the proposed causal explanation. Read the best contrary result and successful historical baseline, including retained checkpoint ancestry. Ask what observation would make the proposed explanation wrong, and whether the plan can produce that observation.

Check whether the intervention changes the claimed mechanism: a drift monitor is not a retention loss; freezing action rows does not necessarily freeze a shared controller; a frozen hybrid controller is not a learned single policy. A successful action-subset intervention can localize a sufficient remedy in that setting but does not establish which training gradient caused the failure. A failed hybrid can reflect incompatibility and need not exonerate either component.

List only the competing explanations that change the next decision. For each, name existing supporting/contradicting evidence and the smallest feasible discriminator. Audit missing controls, bundled changes, changed initial states, seed/noise provenance, unequal exposure, survivor selection, and criteria chosen after seeing outcomes. Reuse established checks when their assumptions still hold.

## Turn criticism into a corrected experiment

Distinguish implementation validity, physical capability, style/task quality, and deployment acceptance. Evaluate metrics in physical units and at the relevant phase/event. Check whether the tested distribution matches the claim: own-policy noise, fixed stress noise, narrow placement grids and broad DR are different scopes. Avoid correcting the objective away from the user's task merely to pass a convenient proxy.

Preserve failed predeclared criteria as historical decisions. A proxy or threshold may itself be questioned, but propose a new, justified measurement or protocol revision before a new comparison; do not retrospectively relabel the failed run as accepted. Keep a fixed longitudinal capability baseline distinct from a changing training initializer.

Choose one concrete disposition: proceed as designed, make a specified correction, run one discriminating diagnostic, or stop this uninformative direction. State the consequential flaw, evidence, repair and what remains unidentified. Predeclare budget, exposure, stopping and next action. Do not let critique become unlimited diagnostic work or a permanent refusal to train.

When both correction and execution are authorized, implement the corrected plan, verify the changed mechanism, and continue into the bounded experiment. Read-only review alone does not authorize training. Record plan revisions in the experiment and project direction files. If an underlying skill caused the flawed design and maintenance is authorized, use `reflect-skills` to repair it with the same evidence limits.
